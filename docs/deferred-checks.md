# Checks deferred to packaging (task 9.1 and later)

F1 verifies the unpackaged build (`electron .` on the built `out/`, and `electron-vite dev`) on one Linux machine: Debian 13, GNOME/Wayland, x64, unprivileged user namespaces enabled. The following are **not** verified by F1 and must be covered by L8 tasks before any release claim.

Unpackaged builds run with default fuses. | 9.1 |
| Packaged behavior | Branches keyed on `app.isPackaged`: DevTools disabled, dev-server override ignored (the override is already compiled out of non-dev builds, tested). Serving `app://` content out of an ASAR archive (`fs.readFile` on archive paths). | 9.1, 9.2 |

## Windows preview (2026-11-08)

| Area | Outcome | Evidence |
|---|---|---|
| Windows commands | **Windows: preview. Run from source; verified in CI on Windows Server 2025. No Windows package yet.** The Windows platform reports itself as supported: commands start, log and stop from the app through the composed platform. The command resolver (`Path` with `PATHEXT`, never the working directory), the `cmd.exe` route for batch files and shell mode, the inherited environment with names merged regardless of case, the editor launch, and output decoding (a UTF-8 console, then the ANSI code page per line) are tested natively on `windows-2025` for every pull request and push to `master`. The end-to-end suite runs there too, against the built app: its portable specs on both systems, Linux-only tests skipped with the facility they need, and Windows-specific specs for what differs (crash recovery ends the trees, the helper is found; until W3 also that the Ports view had no port inspection, which `ports.spec.ts` now checks on both systems) ([ci.md](ci.md#end-to-end-tests-on-windows)). | Windows packaging and helper placement | Unchanged, owned by W4: there is no Windows package. The helper is below the application path, which in a packaged app is inside `app.asar`, from which no executable can be started, so W4 must ship it outside the archive and check its install directory's permissions. The helper is unsigned until the signing decision (G-6); W4 repeats the smoke test as a standard user. Closed on 2026-11-13, see [Windows packaging](#windows-packaging-2026-11-13). | `src/main/platform/index.ts` (`windowsHelperPath`), [Windows process supervision](#windows-process-supervision-2026-11-06) |
| Windows port inspection | **Preview since W3 (2026-11-11), verified in CI on Windows Server 2025 by the integration tests.** The Ports view lists the listening TCP sockets, IPv4 and IPv6, with their owners, through the helper's `ports` subcommand, which opens other processes for querying information only. A command's ports are attributed by PID and creation time, a PID reused after the tables were read is never shown as the owner (a 20 ms time fence), and a holder the user may not query is restricted, which the CI job checks by running the helper as a standard user. `--smoke-test` now fails when ports cannot be listed on Windows, as on Linux. Not verifiable on the runner: a real PID reuse between the reads, and Veydr itself running as a standard user ([ports.md](ports.md#windows-preview)). | Windows handle inheritance | Known limit, not changed in W2. Node starts every process with all of Veydr's inheritable handles (libuv calls `CreateProcessW` with `bInheritHandles`), so the helper, the commands, and a detached editor inherit them. For a normal launch Veydr has none that matter. When Veydr's own stdio are pipes, as when it is run from source with its output captured, a process Veydr started keeps those pipes open, and whoever reads them waits for it: the Windows end-to-end run showed this, Playwright waiting for the editor. A fix starts processes with an explicit handle list (`PROC_THREAD_ATTRIBUTE_HANDLE_LIST`) through the helper; it is a design change for a later change. | First Windows end-to-end run (#45); `test/e2e/commands.spec.ts` (the editor test quits Veydr itself) |

## Windows packaging (2026-11-13)

| Area | Outcome | Evidence |
|---|---|---|
| Windows packaging and helper placement | **Done (W4, OpenSpec change add-windows-packaging). Windows: preview. Unsigned installer; verified in CI on Windows Server 2025.** `npm run dist:windows` builds the helper from source, then an x64, per-user, one-click NSIS installer, `Veydr-X.Y.Z-x64-setup.exe`, configured in `electron-builder.yml`; it installs to `%LOCALAPPDATA%\Programs\veydr` without administrator rights ([install-windows.md](install-windows.md)). The packaged helper is `resources\veydr-helper.exe`, beside `app.asar`, and a packaged app looks for it there; an unpackaged one keeps `out-helper\`. In CI the package holds no executable inside the archive and no update metadata; the unpacked build and the installed app pass `--smoke-test`, the platform check included; a command tree starts and ends through the installed helper; reinstalling and a silent uninstall that keeps `%APPDATA%\Veydr` work. The install directory and every installed file grant write access to the installing user, SYSTEM and Administrators only, the profile's inherited default; Veydr does not check it at runtime ([install-windows.md](install-windows.md#permissions-of-the-install-directory)). A temporary standard user installs, checks the permissions, runs the installed helper and the installed app's smoke test, and uninstalls; the smoke test passed for that account.
