# Dependencies

All direct dependencies are pinned to exact versions (`test/unit/package-policy.test.ts`). Every locked package resolves from `registry.npmjs.org` with a sha512 integrity hash. `.npmrc` sets `engine-strict=true` and `min-release-age=7`, and `package.json` requires npm `>=11.19.0`. That is the npm version F1 was developed and verified with, not a proven minimum: `allowScripts` support first appears in npm 11.16.0 (11.15.0 and 11.14.0 have no allow-scripts code; checked by unpacking the release tarballs), and an npm older than that would silently ignore the key and run install scripts. The key's enforcement was checked on 11.19.0: with it, `electron-winstaller`'s install script does not run in `npm ci`; without it, it does.

## Install scripts

Only `electron-winstaller` (Windows installer, via `electron-builder`) and `fsevents` (macOS file watching, optional) have install scripts; both are set to `false` in `allowScripts`, and the policy test fails if a new locked package with an install script has no explicit decision. Electron 44 downloads its binary lazily on first use (`scripts/ensure-electron.cjs` resolves it before E2E runs).

## `npm audit` (8 moderate, accepted)

All eight entries are one advisory, `sprintf-js` ≤ 1.1.3 DoS through unbounded precision specifiers (GHSA-hp3w-g68c-fv3c, CWE-1284, CVSS 5.3), propagated through:

`electron-builder` → `app-builder-lib` → `@electron/get@3.1.0` → `global-agent` → `roarr` → `sprintf-js`

* `npm audit --omit=dev` reports **0 vulnerabilities**: the shipped dependency tree (`zod`) is clean.
* Build-time only: `electron-builder` is a devDependency and none of this ships in the application. Electron's own downloader is `@electron/get@5.1.0`, which is not affected.
* Not exploitable in practice: it needs attacker-controlled format strings in `roarr` logging inside `global-agent`, which is active only behind proxy environment variables.
* The only fix `npm audit` offers is a downgrade of `electron-builder` to 26.5.0, which trades an unreachable DoS for older tooling. Not applied.
* **Revisited at packaging (task 9.1, 2026-10-25)**: with the unchanged lockfile, `npm audit` and `npm audit --omit=dev` both report **0 vulnerabilities**; nothing to apply.

## Packaging toolchain (task 9.1)

`npm run dist:linux` runs `electron-builder`, which downloads its Linux tools on first use into `~/.cache/electron-builder` from the `electron-userland/electron-builder-binaries` GitHub releases, each checked against a SHA-256 hash pinned in `app-builder-lib`: `appimage-12.0.1` (AppImage runtime and `mksquashfs`), `fpm-1.17.0-ruby-3.4.3-linux-amd64` (builds the `.deb`), and `7zip`. It also fetches the Electron 44.9.3 release archive for the package through `@electron/get` (checksum-verified). The user approved these downloads in chat on 2026-10-25, together with gate G-5. No new npm dependency was added: fuses are applied by electron-builder's own `@electron/fuses`, and the packaging tests parse the fuse wire and the ASAR header themselves.

**Windows (add-windows-packaging, task 2.6).** `npm run dist:windows` runs on Windows only and builds the helper from source first (see below). electron-builder then downloads its NSIS toolchain from the same `electron-builder-binaries` releases, each checked against a SHA-256 hash pinned in `app-builder-lib` (`toolsets/windows.js`): `nsis-3.0.4.1` (`makensis`) and `nsis-resources-3.4.1` (the NSIS plugins), with the Electron 44.9.3 Windows archive through `@electron/get`. The W0 probe built the same NSIS installer this way (`docs/windows-evidence.md`, `nsis-build`). It sets the version strings and the icon of `Veydr.exe` with `resedit`, in JavaScript, and signs nothing: the CI step sets `CSC_IDENTITY_AUTO_DISCOVERY=false` and no certificate (design D8, gate G-6, confirmed by the maintainer on 2026-11-12). The Windows CI cache is off, so the toolchain is downloaded and verified on every run. Still no npm dependency is added: the tests read `electron-builder.yml` with the `js-yaml` that electron-builder itself loads it with, and the archive with their own reader.

## Windows process-tree helper (gate G-4, 2026-11-03)

The maintainer approved option C of `assess-windows-platform` for Windows process trees on 2026-11-03: a small helper program, `veydr-helper.exe`, that owns each command's Job Object. It is not an npm dependency and adds no package, and `electron-builder.yml` and `package-lock.json` are unchanged.

* **Built from source, never committed.** The source is one C# 5 file, `src/main/platform/windows/helper/veydr-helper.cs`. `node scripts/build-windows-helper.mjs` compiles it with the `csc.exe` that .NET Framework 4.8 provides on Windows (`%WINDIR%\Microsoft.NET\Framework64\v4.0.30319\csc.exe`, with `/optimize+ /warnaserror+`) into the git-ignored `out-helper/`, and skips the build while the SHA-256 of the source, stored next to the binary, is unchanged. The `windows` CI job builds it each run (see [ci.md](ci.md)); a policy test fails if a binary is committed under the helper's source or build directories.
* **No toolchain beyond Windows itself.** It needs no SDK, NuGet package or native toolchain. It is compiled in development, in tests, and in CI, and is not compiled on the user's machine. The Windows package ships it as `resources\veydr-helper.exe`, beside `app.asar`, compiled from the committed source by `npm run dist:windows` in the run that builds the package (add-windows-packaging design D2).
* **Unsigned until G-6.** The helper is not signed, and signing is a separate gate (G-6, decided with the Windows packaging). An unsigned executable started from the app directory may be flagged by antivirus or SmartScreen; the app starts it for every command since the Windows preview (W2, run from source), and the risk is listed in [deferred-checks.md](deferred-checks.md#windows-preview-2026-11-08).
* **It grows with the Windows work.** It has the subcommands `version`, `run` (runs a command in a Job Object and stops it), `inspect` and `terminate` (find and end survivors after a crash), and `ports` (lists the listening TCP sockets and their owners). The port inspection (W3) added `ports` to the same file, as planned.
* **Protocol version 3 (W3).** `veydr-helper.exe version` prints `3`, and Veydr refuses a helper that prints anything else, naming the helper and both versions (a version 2 helper, built before `ports`, is refused as "speaks protocol version 2, but Veydr needs version 3"); a stale build is replaced by `node scripts/build-windows-helper.mjs`, which rebuilds when the source changes. `run`, `inspect` and `terminate` are unchanged from version 2.
  * **`ports`.** `veydr-helper.exe ports` takes no arguments, reads nothing on stdin, and prints one JSON line (`src/main/platform/windows/protocol.ts`, `parsePortsOutput`, at most 16 MiB). It reads the time first, then the IPv4 and IPv6 listening tables with `GetExtendedTcpTable`, then opens each owning process with `PROCESS_QUERY_LIMITED_INFORMATION` only. An owner it may not open is `restricted`, one that has exited is `gone`, and one created after the tables were read, or less than 20 ms before, is `reused` and never shown as the holder (its PID may have been given to a new process). A table row with port 0 is dropped, since a listening socket always has a port, and a socket without an owning process (PID 0) is listed with its owner `gone`. If either table cannot be read, the whole listing fails, also on a system without an IPv6 stack (`ERROR_NOT_SUPPORTED`). It starts, signals and ends no process; a unit test checks its C# source for that (`test/unit/port-service.test.ts`).
* **Protocol version 2 (W2).** The form is `veydr-helper.exe run <pipe>`: only the control pipe's name is on the helper's command line. Veydr writes two lines on the helper's stdin and closes it: a one-time token, then `{"application":"<program>","commandLine":"<command line>"}`. Veydr builds the complete command line itself (`src/main/platform/windows/command-line.ts`, unit-tested on every system), so it never passes through the helper's own command line, and the 32,767-character `CreateProcess` limit applies to it exactly.
  * **Read after the handshake, refused on the pipe.** The helper reads the second line only after it has connected to the pipe and proven itself, and reports every refusal as an `error` line there, never on stderr, which belongs to the command and goes into its log. It parses the line strictly by hand (C# 5 has no JSON parser without further references): the two string fields in that order, the JSON string escapes, valid UTF-8 and UTF-16, at most 1 MiB, ended by `\n` alone, and nothing after it. A refusal names an offset or a limit, never the text, which may hold a secret.
  * **Checked, then passed on unchanged.** It refuses NUL, a program that is not a full drive or UNC path (a relative, drive-relative or root-relative path, a `\\.\` or `\\?\` path, a data stream such as `run.bat::$DATA`, a path with a `"` or a line break, or one with an empty, `.` or `..` segment, which normalization would remove, as in `run.bat\.`), an empty command line or one beyond 32,767 characters, a command line whose argv[0] is not the quoted program, and a batch file (`.bat` or `.cmd`, in any case, with trailing dots and spaces removed) given as the program. `CreateProcess` would run such a batch file through `cmd.exe` with its own unsafe quoting; a batch file runs only as part of a `cmd.exe` command line that Veydr built, whose program is `cmd.exe`. Everything else goes to `CreateProcess` exactly as received.
  * **A UTF-8 console.** Each command runs in a hidden console that holds only its own processes, set to output code page UTF-8 (65001) before the command starts, so console programs such as `cmd.exe` write UTF-8 rather than the OEM code page (437 or 850). The helper starts itself as `veydr-helper.exe console`, a short-lived console host outside the command's job. The host creates that console, refuses one shared with other processes, and sets the code page. The helper creates the suspended command on the host's console, attached to it only until the command is created, and the host exits once the command runs on the console, before Veydr hears that the command started. The host is one more short-lived process per command; if it does not answer within 5 s, the command gets a console of its own. The `started` report says whether that worked (`utf8Console`) and gives the system's ANSI code page (`ansiCodePage`). If it did not, the command still runs in a console of its own, and Veydr logs `process.windows-console-not-utf8` with the reason; console programs' non-ASCII output is then shown wrongly.

## Version choices

* **Electron 44.9.3**: latest 44.x patch when pinned. 45.0.0 followed on the same day (2026-10-21; 44.9.3 at 03:31Z, 45.0.0 at 06:03Z, per the registry) and was deliberately not adopted: a new major with no soak time. Adopt a newer major deliberately, from the stable line, when its first patch releases ship. Electron releases a major roughly every eight weeks and supports only the latest few majors, so schedule a re-evaluation at each group review.
* **TypeScript 6.0.3**: `typescript-eslint@8.72.0` peers `typescript >=4.8.4 <6.1.0`; TypeScript 7 is outside that range.
* **Freshness**: several G-1 pins were published within days of installation (`@tanstack/react-virtual` the same day, `vite` and `electron` about a day before). Lockfile integrity matches the registry. `.npmrc` now sets `min-release-age=7`, so any *new* resolution (`npm install`, `npm update`) refuses versions younger than seven days; `npm ci` follows the lockfile and is unaffected, so the existing young pins remain until they are deliberately bumped. A security fix may justify an override (`--min-release-age=0` for that one command, recorded in the review). Verify `npm ci` and `npm audit` after any bump.
* **`@tanstack/react-virtual` 3.14.22** is on the G-1 approved list (design D13) and stays pinned. Nothing imports it until log virtualization (group L6). It was published the same day it was installed; the lockfile integrity hash matches the registry's. Because it is unused, it is not part of the shipped app (devDependency, bundled only when imported). At the start of L6, re-check its publish date and advisories and bump only deliberately. No G-1 dependency was added or removed during F1 review.
